Beta 74 closes the hole beta 72.1 named: fast save in 2K5 Mod Studio, and opening and fast saving a project in APF 2K8 Mod Studio, now compare the full project's SHA-256 on every check. Another program's same-size rewrite is refused even if it restores the old modification time and Windows reports the same creation time. This is a full-file hash, with no sampling or skipped regions.

Changes only to change time still open and save normally. A changed size, modification time or file ID still refuses with the existing messages. A refused open keeps the current workspace, and a refused save leaves the externally changed file intact.

The standalone unittest file `tests/mod_editor/test_b721_change_time_identity.py` proves the three refusals with `test_fast_save_full_sha256_refuses_same_size_rewrite_restored_mtime`, `test_apf_open_full_sha256_refuses_same_size_rewrite_restored_mtime`, and `test_apf_fast_save_full_sha256_refuses_same_size_rewrite_restored_mtime`. Each flips bytes at the start, beyond the first hash block and at the end, restores modification time, and repeats with change time frozen in the Windows shape. All 18 cases failed against the beta 72.1 implementation because it accepted the changed file.

On a real 28,675-byte project containing one portrait replacement, 51 warm-cache Linux measurements put the median 2K5 save guard, atomic publication and post-save identity capture at 0.693 ms before and 0.746 ms after, an increase of 0.053 ms. This measures the affected save boundary, excluding serialization and GUI work. The APF boundary on the same byte workload measured 0.179 ms before and 0.224 ms after; that is a comparison workload, not a real APF project timing. These are local measurements, not a claim about large projects or Windows storage speed. Native Windows and macOS runs remain for CI.
